# Хэллоуин 2026: ТЗ для Android

Что появляется на общем бэкенде ProtoMap к Хэллоуину и что нужно сделать в приложении. Ивент идёт **с 20 октября по 2 ноября 2026 включительно**. Окно продаж на сервере открывается 20.10 в 00:00 по Минску и закрывается 03.11 в 00:00.

Тут всё, что понадобится: правила, контракты функций, геометрия рамок и фонов, анимации с числами, тексты. Ссылки на код сайта даны от корня веб-репозитория ProtoMap, в нём лежит первоисточник.

Ссылки на код приложения — по копии от 15.07.2026 (`versionName 1.0.22.dev4`, `versionCode 179`), которая лежит у Ориона. Если код с тех пор уехал, ищи по именам. `$P` — это `app/src/main/java/by/iposdev/protomap`.

> **Для Claude в репозитории приложения.** Бэкенд (Cloud Functions, правила Firestore) живёт в веб-репозитории, отсюда его не поменять: всё серверное — через Ориона. Граница доверия та же, что для остальной экономики: **клиент показывает и просит, решает сервер.** Цену, окно продаж, исход Плинко, выдачу приза, множитель Краша считает сервер. Клиентские проверки из этого ТЗ нужны для удобного интерфейса, а не для защиты. Не пиши в `users/{uid}.owned_items`, `casino_credits` и `shop_items` с клиента: правила это и так запрещают, обходить их не нужно.

## Порядок выката и что увидит старая версия

1. Функции и сайт выкатываются вместе: `purchaseShopItem` с проверкой окна и скрытости, `playPlinko` с призом, `getPlinkoState`, `cashOutCrashGame`.
2. После этого скрипт `scripts/seed-halloween-shop.mjs` создаёт 8 документов в `shop_items`. До этого новых id нет ни в базе, ни у пользователей.
3. 20.10 в 00:00 открывается окно: товары появляются на витрине сайта, начинает разыгрываться приз.

Дату шагов 1–2 Орион скажет отдельно. Что при этом будет с версией, где нет правок из этого ТЗ:

- **Тыквенную голову** версия от 15.07 не покажет: у документа `is_hidden: true`, а `ShopViewModel` такие отбрасывает.
- **Остальные 7 товаров** будут на витрине приложения с момента шага 2, то есть и до 20.10, и после 2 ноября. Вне окна покупка упадёт с ошибкой «Этот предмет сейчас не продаётся.» Это текст сервера, `ShopViewModel` покажет его как есть. Внутри окна покупка пройдёт.
- **Отрисовка.** Рамки нарисуются стандартным голубым кольцом (`FrameType.fromDbValue` → `else -> DEFAULT`), фоны — как фон по умолчанию (`BackgroundType.fromId` → `DEFAULT`). Ничего не падает, но купленное в приложении не видно, видно только на сайте.

Отсюда минимум для релиза до шага 2: фильтр по окну (раздел 1) и пять рамок с тремя фонами хотя бы в облегчённом виде (разделы 2–3).

## 1. Магазин: окно продаж

### Поля `shop_items`

| Поле | Тип | Смысл |
| --- | --- | --- |
| `is_hidden` | `boolean` | `true` — в магазине нет, предмет только выдаётся. Это поле приложение уже понимает. Теперь его понимают и сайт, и `purchaseShopItem`. |
| `available_from` | `Timestamp` | **новое.** Начало окна продаж, включительно. Нет поля — без начала. |
| `available_until` | `Timestamp` | **новое.** Конец окна, **не** включительно. Нет поля — без конца. |

Остальные поля как были: `name`, `description`, `price`, `type` (`"frame"` или `"background"`), `style_value`. У новых товаров `style_value` равен id документа, а id фонов начинаются с `bg_`. На этом держатся вкладки магазина (`CasinoShopScreen.kt:247-250`) и инвентарь, который берёт рамку по id документа, а не по `style_value` (`InventoryViewModel.kt:109-110`, `InventoryScreen.kt:222`).

### Правило «продаётся сейчас»

Предмет продаётся, если одновременно:

1. его id не в списке скрытых: `frame_dev`, `frame_beta`, `frame_ludoman`, `frame_aurora`, `frame_cryo`, `frame_festive`;
2. `is_hidden != true`;
3. `available_from <= сейчас < available_until` (отсутствующая граница не ограничивает).

Первоисточник — `functions/src/shopRules.ts`. По нему работают `purchaseShopItem` и витрина сайта. Раньше скрытые предметы прятала только страница сайта, а функция продавала их любому, кто вызовет её напрямую. Теперь отказывает и функция.

В приложении это `ShopViewModel.kt:49-69`. Сейчас там фильтр `!item.isHidden && !blacklistedFrames.contains(item.styleValue)` со своим списком (`:40-42`): `frame_dev`, `frame_beta`, `dev-frame`, `beta-frame`, `frame_ludoman`. Нужно добавить окно и привести список к серверному. В модель `data/model/ShopItem.kt` — два поля:

```kotlin
@get:PropertyName("available_from") @set:PropertyName("available_from")
var availableFrom: Timestamp? = null,
@get:PropertyName("available_until") @set:PropertyName("available_until")
var availableUntil: Timestamp? = null,
```

```kotlin
private val HIDDEN_ITEM_IDS = setOf(
    "frame_dev", "frame_beta", "frame_ludoman",
    "frame_aurora", "frame_cryo", "frame_festive",
)

fun ShopItem.isOnSale(now: Timestamp = Timestamp.now()): Boolean {
    if (id in HIDDEN_ITEM_IDS || isHidden) return false
    val from = availableFrom
    val until = availableUntil
    return (from == null || now >= from) && (until == null || now < until)
}
```

Тест `app/src/test/.../ui/casino/shop/ShopFilterTest.kt` копирует старый фильтр, его надо обновить вместе с ним.

Время на устройстве можно подкрутить, и тогда витрина покажет товар раньше срока. Это не дыра, сервер всё равно откажет.

`frame_cryo` — рамка зимнего ивента, в продаже её больше нет. Сервер её не продаёт, а скрипт товаров ставит ей `is_hidden: true`, так что из витрины приложения она уйдёт и без релиза. У купивших она остаётся в инвентаре.

### Админка приложения стирает окно — исправить до выката

`admin/.../ui/admin/shop/AdminShopViewModel.kt:62` сохраняет товар через `collectionRef.document(docId).set(item)` без merge. Модель не знает `available_from` и `available_until`, поэтому **любая правка хэллоуинского товара из админки сотрёт окно**. Товар начнёт продаваться круглый год, а приз Плинко станет разыгрываться бессрочно. Исправление — `set(item, SetOptions.merge())` или `update()` только изменённых полей. Пока это не в релизе, хэллоуинские товары из админки приложения не трогать.

На карточке товара с окном сайт показывает плашку с последним днём продаж: `available_until` минус 1 мс, дата по `Europe/Minsk`, формат «день месяц». Получается «До 2 ноября». Тексты в справке Б.

## 2. Рамки

### Файлы

Все картинки лежат в веб-репозитории в `static/halloween/cosmetics/`. После выката они доступны по `https://proto-map.vercel.app/halloween/cosmetics/<файл>`.

| Файл | Что это |
| --- | --- |
| `<id>.svg` | полная рамка; у листьев, паучков и паутины внутри SMIL-анимация |
| `<id>-lite.svg` | облегчённая, неподвижная, для маленьких размеров |
| `frame_cat_familiar-eyes.svg` | только глаза кота, отдельный слой для моргания |

### Геометрия

Каждая рамка — квадрат `viewBox="0 0 200 200"`. Аватар в нём — круг с центром (100, 100) и радиусом 50. Значит:

- слой рамки **вдвое больше круга аватарки** и стоит с ним по одному центру;
- рисуется **поверх** аватарки;
- **не обрезается** ни по кругу, ни по контейнеру. Кот лежит сверху и выходит над аватаркой, тыква шире неё, паучки висят снизу.

В приложении `FramedAvatar` (`ui/common/ProfileFrames.kt:88-183`) рисует картинку кругом в 90% от `size` (`:139-155`). Значит, слой хэллоуинской рамки — `1,8 × size` по тому же центру, без обрезки:

```kotlin
// внутри FramedAvatar, для хэллоуинских FrameType
Box(Modifier.size(size), contentAlignment = Alignment.Center) {
    // ... аватар, как сейчас: 0.9 × size, clip(CircleShape)
    HalloweenFrameLayer(frameType, Modifier.requiredSize(size * 1.8f)) // requiredSize — выйти за границы
}
```

Если у кого-то из родителей стоит `clipToBounds` или `clip(...)`, кот и паучки обрежутся. На метках карты (`MapScreen.kt:2076-2087`) и в строках чата это стоит проверить первым.

### Сейчас в приложении

`FrameType` (`ProfileFrames.kt:40-67`) — закрытый enum, `fromDbValue` сопоставляет id через `when`, неизвестный id даёт `DEFAULT` (`:63`). Для каждой новой рамки нужны:

- значение enum;
- строка в `fromDbValue`: `"frame_cat_familiar" -> CAT_FAMILIAR` и так далее;
- отрисовка в слоях `FramedAvatar` (`:119-136`, `:173-181`).

Рамка показывается везде, где уже есть `FramedAvatar`: профиль (`ProfileScreen.kt:337-341`, 115 dp), метка карты (36 dp) и попап (64 dp), меню навигации карты (48 dp), сообщения чата (36 dp), шапка личного чата, список диалогов, комментарии профиля, рейтинг шагомера, магазин, инвентарь.

### Где какая версия

На сайте полная версия с анимацией стоит там, где аватар крупный: профиль (128 px), магазин (100 px), инвентарь (70–150 px). Облегчённая — на метке карты (38 px), в попапе карты и лидерборде казино (48 px), в комментариях (42 px). Для приложения порог такой: `size` меньше 64 dp — облегчённая.

На метке карты у рамки своё кольцо, поэтому стандартную обводку и свечение метки под ней сайт убирает.

### Как отрисовать

Все рамки приложения нарисованы кодом в Compose. Хэллоуинские — готовая графика, и перерисовывать её кодом долго. Варианты:

1. **SVG через Coil (рекомендую).** В приложении Coil 2.7.0, но только `coil-compose`, SVG он не декодирует. Нужны `io.coil-kt:coil-svg:2.7.0` и `SvgDecoder.Factory()` в общем `ImageLoader` (через `ImageLoaderFactory` в `Application`). Файлы лучше положить в `app/src/main/assets/halloween/` и грузить как `file:///android_asset/halloween/<файл>`. Так не нужна сеть и не зависишь от Vercel, а на карте десятки меток. Под капотом AndroidSVG: маски, градиенты и clipPath он рисует, SMIL не проигрывает. Значит, полный `.svg` в приложении будет неподвижным. Бери `-lite.svg` везде, а анимацию добавляй поверх (пункт 2).
2. **Анимация в профиле поверх облегчённой версии.** Подвижные детали из таблицы выше — в Compose через `rememberInfiniteTransition`. Глаза кота — отдельный слой `-eyes.svg` с `alpha`. Свеча — `drawCircle` с `Brush.radialGradient`. Паучки — `graphicsLayer { rotationZ; transformOrigin }` вокруг точки подвеса. Для этого статичную часть и подвижные детали придётся разделить — проще всего попросить у Ориона отдельные SVG деталей.
3. **VectorDrawable** не подойдёт без доработки. В Тыквенной голове есть `<mask>`, в глазах кота и слоях мерцания фонов — размытие `<filter><feGaussianBlur>`. VectorDrawable не умеет ни того, ни другого.

Размытие AndroidSVG пропускает: детали рисуются, но резкими. На глазах кота это почти не заметно. Мягкость можно вернуть через `Modifier.blur` (API 31+).

| --- | --- |
| `<id>.svg` | сцена 1600×1000: небо, луна, дальний план |

### Масштаб и кадрирование

Фон заполняет экран как `ContentScale.Crop`, но с **точкой фокуса по горизонтали**. На широком экране видна середина сцены. На вертикальном видна узкая полоса, и если оставить середину, на экране останутся звёзды и трава: луна, тыква, кот и замок стоят по краям. Поэтому на вертикальном экране полоса сдвигается к герою сцены. В приложении экран почти всегда вертикальный, так что это главный случай.

```
k     = max(W / 1600, H / 1000)          // масштаб: единица сцены → пиксели
fx    = 0.5, если W ≥ H; иначе fxPortrait из таблицы
offX  = (W − 1600·k) · fx                // ≤ 0: на сколько сцена уехала влево
offY  = (H − 1000·k) / 2
сцена и силуэты: с (offX, offY), размер 1600k × 1000k
мерцание:        с (offX + x0·k, offY + y0·k), размер w·k × h·k
```

| id | fxPortrait | Коробка мерцания x0, y0, w, h | Что мерцает | Анимация |
| --- | --- | --- | --- | --- |
| `bg_moonlit_night` | 0.95 | 1301.36, 777.08, 99.94, 62.12 | рожица тыквы | «дыхание» |
| `bg_cat_on_fence` | 0.95 | 1316.39, 564.62, 110.84, 38.06 | глаза кота | моргание |
| `bg_castle_on_hill` | 1.0 | 1269.63, 536.80, 126.09, 204.23 | окна замка | дрожание |

Анимации меняют только прозрачность слоя мерцания, сцена неподвижна:

- **«Дыхание»:** 0,35 ↔ 1 за 3,6 с в каждую сторону, ease-in-out.
- **Моргание:** цикл 5,5 с, от 92% до 96% слой скрыт, ступенькой.
- **Дрожание:** цикл 5 с, ease-in-out между точками: 0% → 1, 18% → 0,55, 22% → 0,9, 47% → 0,4, 53% → 0,85, 78% → 0,5, 83% → 1, 100% → 1.

## 4. Плинко

Новая игра казино. Делать её в приложении или нет, решаете вы с Орионом. Ниже — всё, что нужно, если да. В приложении её пока нет. Лобби — `GameDef` в `ui/casino/GamesScreen.kt:740-806`. Включение — через флаг в `mobileapp/feature_flags`, по образцу `slots_enabled` (`FeatureFlagService.kt:195-203`). Например, `plinko_enabled`: тогда Орион сможет закрыть игру без релиза.

### Правила

- **Открывается 20 октября 2026 в 00:00 по Минску** вместе с Хэллоуином и дальше остаётся насовсем; приз — только в окне ивента. До открытия сайт игру не показывает, а `playPlinko` отвечает `failed-precondition` «Плинко откроется 20 октября.». В приложении — то же: карточку в лобби показывать по `open` из `getPlinkoState`.
- Доска: 16 рядов штырьков, 17 лунок. На каждом ряду шарик отскакивает влево или вправо, лунка — число отскоков вправо (0…16).
- Выплата за лунку в десятых долях ставки, слева направо: `500, 250, 120, 60, 30, 15, 7, 4, 3, 4, 7, 15, 30, 60, 120, 250, 500`. То есть ×50, ×25, ×12, ×6, ×3, ×1,5, ×0,7, ×0,4, ×0,3 и зеркально. Выплата = `floor(ставка × десятые / 10)`.
- Шанс лунки k — C(16, k) / 2¹⁶. Возврат — 89,6%. Примерно 4 шарика из 5 теряют часть ставки, ×50 выпадает 1 раз из 32 768.
- Ставка за шарик — от 10 PC до лимита. Лимит = `min(500, floor(банк / 1000))`, то есть 0,1% общего банка казино. Если лимит меньше 10, игра закрыта.
- За бросок — от 1 до 10 шариков (на сайте кнопки 1, 5, 10; ставка шагает по 10). Списывается `ставка × шарики`.
- 30 бросков в минуту на игрока.

**Сумму банка игрокам не показываем** — ни в интерфейсе, ни в логах на устройстве. Показываем только лимит ставки: «Ставка до N PC за шарик». Функции банк не отдают.

### Контракты

`getPlinkoState({})` — перед игрой: открыта ли игра, лимит и разыгрывается ли приз. Ответ: `{data: {open, maxBet, prizeAvailable}}`.

`playPlinko({bet, balls})` — бросок. Ответ:

```json
{
  "data": {
    "drops": [{"path": [0,1,1,0,…], "slot": 7, "payout": 7, "prize": false}],
    "stake": 100,
    "win": 64,
    "newBalance": 1964,
    "maxBet": 73,
    "prize": null
  }
}
```

Функции казино оборачивают результат в `data`. В Kotlin это `(result.data as Map<*, *>)["data"]`, а не сам `result.data`. Пример — в справке А, ошибки — там же.

### Анимация

Исход решён до анимации: `path[r]` — отскок на ряду r (0 — влево, 1 — вправо), `slot` — сумма `path`. Анимация только показывает путь, шарик обязан лечь в `slot`.

Как сделано на сайте (`src/lib/client/plinkoBoard.ts`), если хочется так же:

- Геометрия в единицах доски: шаг штырьков 24, шаг рядов 21, первый ряд на y = 26, отступ по бокам 14. Радиус штырька 2,4, шарика 5,2. В ряду r стоит r + 3 штырька. Лунки высотой 26 с зазором 3. Ширина доски — `17 × 24 + 28 = 436`.
- Полёт — баллистика: между ударами шарик летит по параболе (тяжесть 2400 ед/с²). Подскок у каждого удара случайный, но дуга рассчитана так, чтобы попасть в бок нужного штырька следующего ряда. Иногда (22%) шарик сначала подпрыгивает на макушке. Дуги проверяются, чтобы не проходить сквозь штырьки.
- Шарики одного броска стартуют с интервалом 250 мс.
- **Баланс и история растут, только когда шарик лёг в лунку.** Новый баланс приходит в ответе сразу, но если показать его до приземления, исход виден раньше анимации. На сайте этот баг уже был. Показанный баланс = старый − ставка, дальше `+payout` по одному шарику при приземлении.
- Лимит ставки из ответа (`maxBet`) применяется, когда упал последний шарик броска.
- Цвет лунки — по множителю: <1, <2, <5, <10, ≥10, пять ступеней яркости.
- В Хэллоуин шарик — маленькая тыква: контуры `PUMPKIN_BODY` и `PUMPKIN_FACE` в `plinkoBoard.ts`, `viewBox 0 0 14 14`.

### Приз: Тыквенная голова

- Призовые лунки — крайние, ×12 и выше: **0, 1, 2, 14, 15, 16**. Шанс на шарик — 274 из 65 536, примерно 1 к 239.
- Приз разыгрывается, пока открыто окно документа `shop_items/frame_pumpkin_head` (те же `available_from` и `available_until`) и рамки у игрока ещё нет.
- Первый шарик броска, попавший в призовую лунку, приносит рамку: сервер добавляет `frame_pumpkin_head` в `owned_items` в той же транзакции. У этого шарика `prize: true`, а в ответе `prize: "frame_pumpkin_head"`. Выплата за лунку та же, приз идёт сверху.
- Рамка одна на игрока. Когда она есть, приз из игры пропадает.

В интерфейсе сайта:

- пока `prizeAvailable == true`: над призовыми лунками маленькие тыквы (тот же силуэт, что у шарика, 13×13 ед. над серединой лунки), обводка лунки `#FFF3C4`, под историей подсказка `plinko_prize_hint`;
- когда приземлился шарик с `prize: true`: звук джекпота, окно `plinko_prize_title` / `plinko_prize_text`, тыквы и подсказка исчезают сразу, без перезагрузки.

## 5. Краш: что поменялось

`cashOutCrashGame({gameId, multiplier})`: контракт тот же, поменялось, сколько платят.

- Раньше сервер платил `ставка × multiplier` клиента, если тот не выше точки краша. Неудачная попытка игру не закрывала, поэтому точку можно было нащупать повторными вызовами.
- **Теперь** сервер сам считает, до скольких игра доросла по его часам: `m = floor(e^(0.08 · t) · 100) / 100`, где t — секунды с `createdAt` игры. Платит `min(multiplier клиента, m)`. Если `m` уже дошёл до точки краша, отвечает «Too late», даже если фоновый цикл ещё не отметил краш.
- Чужую игру вывести нельзя (`permission-denied`), забаненному — тоже.
- Ответ: `{data: {winAmount, cashOutAt}}`. RTDB при выводе получает `s: "done"`, `m: cashOutAt`.

В приложении (`ui/casino/crash/DataUplinkViewModel.kt`) это совместимо. Скорость роста та же, `exp(0.08 · t)` (`:149-163`). Отсчёт идёт с момента подписки на RTDB, то есть позже серверного `createdAt`, поэтому множитель на экране почти всегда не выше серверного, и сервер платит ровно показанное. Две правки всё же стоит сделать:

- `cashOut` (`:165-195`) показывает выигрыш `bet × finalMultiplier` до ответа сервера. Лучше после ответа заменить его на `winAmount`: если часы устройства где-то разошлись, игрок увидит то, что получил.
- `CasinoRepository.kt:138-139` читает `winAmount` прямо из `result.data`, а он лежит в `result.data["data"]`.

```kotlin
fun seasonOf(date: LocalDate = LocalDate.now()): Season? {
    val m = date.monthValue
    val d = date.dayOfMonth
    return when {
        m == 4 && d == 1 -> Season.APRIL
        m == 5 && d in 4..10 -> Season.ANNIVERSARY
        (m == 10 && d >= 20) || (m == 11 && d <= 2) -> Season.HALLOWEEN
        m == 12 && d < 15 -> Season.WINTER
        (m == 12 && d >= 15) || (m == 1 && d <= 14) -> Season.NEW_YEAR
        else -> null
    }
}
```

## 7. К сведению: комментарии в каналах

С сентября работают серверные триггеры Firestore (`functions/src/channelComments.ts`, регион `europe-central2`). Схему каналов и групп комментариев задаёт приложение, сервер под неё подстроился:

- `channels/{id}/posts/{postId}.commentsCount` считает сервер: все сообщения топика, кроме `is_deleted == true`. Клиенту его писать не нужно.
- Топик обсуждения сервер создаёт сразу при публикации поста, если у канала включены комментарии.
- Удалили пост — сервер удаляет топик, комментарии и медиа. Удалили канал — удаляет его группу комментариев.
- Группа считается группой комментариев канала, только если ссылки совпадают в обе стороны: `group.linkedChannelId == channelId` и `channel.linkedGroupId == groupId`.
